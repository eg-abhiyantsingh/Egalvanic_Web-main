# ZP-4513 — Add a global Motor Overload node class and an 'MC' symbol for Motor Controller (migration movl_a1)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: backend, migration

## Description

### What's the problem

There was no class for a motor overload relay, so it could not be modeled or exported to SKM as a Protection with ProtectionType 'Motor Overload'. Separately, Motor Controller shared Motor's M-in-a-circle icon, so on the SLD a controller looked identical to a motor.

### What's the solution

One migration, movl_a1 (parent irtemp_a2, single head). Adds a global 'Motor Overload' class (protective role device_role 2, overcurrent protection on, 1 in / 1 out port, not library-backed, no core attributes, SKM Protection with ProtectionType 'Motor Overload' written as-is by the exporter), one override per company that has class overrides (egfab_a1 pattern), and two new global node_icons: motorOverload (thermal overload symbol, two opposed arcs) used by all Motor Overload rows, and motorController ('MC' in a square) which every Motor Controller row still on the stock motor icon moves to - Motor keeps its icon. No FE or iOS viewer change (both render icon.svg from the DB) and no exporter change. Idempotent (NOT EXISTS / ON CONFLICT), every value bound as a parameter; the downgrade restores the motor icon and deletes the new class and icons only where nothing references them. Tested in rolled-back transactions on localdev/dev/qa (dev: 17 overrides, 33 MC rows repointed) and applied on localdev.

### Fixes

* eg-pz-backend #1399 - UI Global node class: Motor Overload + Motor Controller 'MC' symbol
* eg-pz-backend #1408 - Fixed migration sequences: re-parented movl_a1 from irtemp_a2 to qrlabels_a1 after the cicd/dev tip moved, keeping a single alembic head. Migration behaviour is unchanged.
