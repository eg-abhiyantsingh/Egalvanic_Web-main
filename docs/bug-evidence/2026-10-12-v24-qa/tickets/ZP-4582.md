# ZP-4582 — SKM import: namespace SKM ids per project so cross-project studies import correctly

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, backward-compatibility, frontend, migration, schema, ui

## Description

### What's the problem

SKM component ids are only unique within a single SKM project, but the importer merged assets on skm_id alone. Importing a study from a different SKM project therefore silently matched unrelated equipment: it skipped equipment that looked like a duplicate and miswired connections between assets that only happened to share an id. The person importing also had no way to see or control which existing SKM data a new study would merge into.

### What's the solution

Assets now carry an SKM namespace alongside the SKM id, and the importer dedups on (namespace, skm_id) instead of skm_id alone.

* Backend adds nodes.skm_namespace via an idempotent migration; commit dedups on (namespace, skm_id).
* Backward compatible: legacy rows with a NULL namespace still match and are adopted, so existing SLDs are unaffected.
* Import preview suggests a namespace from the PTW header's project folder (falling back to the upload filename) and lists namespaces already on the SLD with overlap counts.
* SKM export renumbers duplicate ids within a single export and warns.
* Frontend adds a required SKM project field on the import review dialog (prefilled from the study header, existing names selectable) and a read-only 'SKM ID . namespace' caption on SKM-imported assets (Asset Details Engineering tab and asset form Engineering header).
* Caveat: the namespace is derived heuristically from the study header; the importer confirms it, and a wrong choice still merges into the wrong namespace.
