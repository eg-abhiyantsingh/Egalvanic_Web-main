# ZP-4592 — Tenant-gate the bulk-edit export / validate / process endpoints

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend

## Description

### What's the problem

The bulk-edit endpoints (export, validate, and process) were not scoped to the caller's tenant. A signed-in user could drive bulk-edit operations against nodes that belong to another company, a cross-tenant data-exposure (IDOR) gap on a high-impact write path. The severity warranted shipping it straight to production as a hotfix before it flowed back through the normal branches.

### What's the solution

Tenant gating was added to the bulk-edit export/validate/process routes in app/routes/bulk_edit_routes.py so every request is scoped to the authenticated user's company, and a focused test file (tests/test_bulk_edit_tenant_gate.py, 5 cases) was added to lock the behaviour in. The fix landed first as prod hotfix #1441, was cherry-picked to QA (#1445) and to dev (#1446). The dev cherry-pick resolved a trivial conflict by keeping both the new tenant gate and dev's own \_hidden_attr_ids helper at the same spot.

### QA Review

Environment: Dev + QA (also already live in prod).

* As a user in company A, attempt bulk-edit EXPORT for nodes owned by company B — confirm the request is rejected or returns only company A's scope, not company B's data.
* Repeat for bulk-edit VALIDATE and bulk-edit PROCESS with another company's node ids — each must be tenant-scoped and refuse cross-company ids.
* Positive case: same-company bulk edit (export/validate/process) still works end to end with no regression.
* Confirm the dev-only \_hidden_attr_ids behaviour (hidden attributes) is unchanged after the conflict resolution.
