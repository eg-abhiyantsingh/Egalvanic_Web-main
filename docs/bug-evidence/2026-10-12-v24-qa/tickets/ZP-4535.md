# ZP-4535 — Journal capture menu: per-class fields validated in the engine, review chips read the menu keys (Console #45)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, frontend, migration, schema, ui

## Description

### What's the problem

In the Site Walk Journal interpreter, the model was given class names and a single fixed list of fifteen node.\* keys for every class, with no menus for select-style fields and no validation of the values it wrote back. A class could be tagged with an attribute it has no field for, and option values (enclosure type, mains type, manufacturer) were spelled however the model chose, so the captured data did not line up with the asset's real fields afterward. On the web review side the attribute chips were keyed to that old fixed list, and the "accepted" hint still read "no longer read" even though accepted walks had gone back to being re-read on every change.

### What's the solution

Engine (ai-pipeline): the prompt now lists, per class, exactly which fields the model may set and what each accepts - a star on arc-flash-critical fields, "when ..." on state-gated ones, options inline, long menus (voltages, manufacturers) once underneath. A new validate_attributes step, copied verbatim from the backend's site_walk_capture_menu so the backend tests stay the contract, runs after every add/update: values that fit are normalised in place, values that do not are removed and sent back through the existing repair round naming the field's menu. The menu's hash seeds the fold chain (FOLD_VERSION -> 2026-10-01.1) so a menu change re-reads the walk, and the Lambda reads the menu.json the backend stages; a job without one folds with the old fixed list. \~3K cacheable tokens for 18 classes.

Frontend: the review chips now read the capture-menu keys (node.ampere_rating for a column, attr.catalogNumber for a class attribute), stripping either prefix and splitting camel case into readable labels. The accepted hint now reads "Accepted - kept up to date", or "Accepted - reading changes" while a re-read is queued, replacing the stale "no longer read".

Caveat: every walk re-folds once on the FOLD_VERSION bump; the Lambda redeploys from cicd/dev on merge. No infra or DB migration.

Backend (late companion, #1413): site_walk_capture_menu.py is the authoritative source the engine's validator was copied from - it derives each class's menu from arc_flash_readiness.RULES, node_star_columns.allowed_headers, the class definition's own attributes (the node column wins over a mirrored attribute) and the enum tables (mains/phase/trip-by-family, manufacturers, voltages), stages it as menu.json, and at release writes the validated node.\* through the bulk-edit writer and attr.\* into core_attributes - no equipment-library binding. It also makes an accepted walk keep being read: each run reuses the interpreter's rows in place (matched by the engine's per-unit uuid in the new site_walk_assets.proposal_uid column, else by class+room+label), and the created asset's node id is that same uuid, so release is idempotent - an existing live node under that id is adopted, not recreated.

### QA Review

Environment: dev only (not yet in QA).

* On dev, open a Site Walk Journal and interpret a walk containing a panelboard/load center. Confirm captured attributes use only fields the class actually has (e.g. a Panelboard gets node.mains_type / node.ampere_rating / node.nameplate_voltage), and that option values match the listed menu exactly.
* In Journal review, confirm attribute chips render readable labels (e.g. "catalog number: SN3048L1125") with the node./attr. prefix stripped and camelCase split.
* Accept a walk, then change something on it; confirm the hint reads "Accepted - kept up to date" (or "Accepted - reading changes" while a re-read is queued), never "no longer read".
* Negative: give a field a value outside its menu and confirm it is dropped/repaired rather than captured verbatim.
* Backend (#1413): after accepting a walk, add a new entry and confirm the accepted walk is re-read automatically with no manual re-read. Release the walk and confirm each journal unit's created asset keeps one id across re-reads - releasing twice adopts the existing node rather than creating a duplicate.
* Note: after deploy every walk re-folds once (FOLD_VERSION bump) - expect a one-time re-read.
