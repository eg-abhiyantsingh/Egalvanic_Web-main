# ZP-4564 — Issues on journal site walks: engine proposes deficiencies, backend mints them at release (task #69)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, frontend, migration, schema, ui

## Description

### What's the problem

During a journal site walk a technician calls out deficiencies out loud ("dead front missing on LP-1", "clearance blocked in front of the MSB"), but none of it could ever become an issue. The interpreter kept these only as free-text condition signals that never left the engine, so they never reached a row and release had nothing to mint. A walk could not surface a single issue.

### What's the solution

The journal engine now proposes issues directly from what the walk says (a photo raises one only when the problem is plainly visible; wear the tech calls sound is condition, not an issue), and the backend persists and mints them. A new site_walk_issues table holds one deficiency per walk-unit or room, with its class details array, journal photos, evidence quotes and the engine uid. The capture menu carries the company's issue_classes (globals never, SCCR excluded as system-minted); validate_issue_details is the canonical validator, copied verbatim into the engine and parity-checked. A strict PUT /site-walk/<id>/issues/<issue_id> endpoint (site_walks.manage) edits class/details/title/priority/hazard/unit/photos/dismissed with tenant, walk-ownership, class, unit and photo-scope checks. Accept carries issues alongside assets; Release mints a real issue per accepted, undismissed walk issue (on the node its unit became, else site-level; photos copied as type issue; origin=site_walk; idempotent via issue_id). A person's edit or dismissal always wins over a re-read. FOLD_VERSION is now 2026-10-02.1, so every journal walk re-folds once on next read. Either deploy order with the backend is safe: an old backend menu has no issue_classes so nothing is proposed, and an old apply ignores issues.

### QA Review

Environment: Dev only (cicd/dev; not yet in QA).

* On a journal walk, speak a clearance obstruction in front of the MSB -> an OSHA Violation issue is proposed on the MSB.
* Speak a missing dead front on LP-1 -> an NEC Violation with immediate hazard on LP-1.
* Mention missing arc-flash labels affecting a whole room -> a single room-level issue (not one per asset).
* Describe wear/surface rust the tech calls solid -> no issue raised (condition, not a deficiency).
* Edit or dismiss a proposed issue, then trigger a re-read -> the edit/dismissal survives (not rewritten or retired).
* PUT an edit with a bad unit, a wrong-company class, a foreign photo, or a bad priority -> refused.
* Release an accepted walk -> one real issue minted per accepted, undismissed walk issue (on its node, site-level if no unit; photos copied). Release again -> mints 0 (idempotent).
* A walk with issues but no units still refuses release (nothing_to_release).
