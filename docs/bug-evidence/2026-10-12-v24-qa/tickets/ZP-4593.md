# ZP-4593 — DC/solar equipment classes, AC/DC connection rule, and company-typed source voltages

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, frontend, migration, schema, ui

## Description

### What's the problem

The SLD had no concept of AC versus DC, so a DC bus could be wired straight to a utility with nothing objecting, and the DC/solar equipment in the PTW model (PV arrays, inverters, DC motors/loads/capacitors, DC protection) had no classes at all. Solar sites also need source voltages such as 1000 VDC that were absent from the global voltage list, with no way to add a company-specific one.

### What's the solution

Added a current_type ('ac'|'dc') concept across node classes and terminal orientations, a full set of DC/solar equipment classes (DC Node Bus, DC Bus, DC Combiner Box, DC Cable, DC breaker/fuse/disconnect, DC Motor/Load/Capacitor/Generator, PV Array, AC PV Array, Rectifier, Inverter), and company-scoped typed-in source voltages via POST /enum-node-voltages/find-or-create (global-first, bounded 1 Vâ€“1 MV, scoped to globals + the caller's company). A reference AC/DC connection rule (app/services/sld_current_type.py) reports current_type_mismatch on /edge/preview-rules; create_edge never rejects (offline-sync precedent ZP-2577), the SLD issues engine flags connection.ac_dc_mismatch instead. SKM XML import/export cover every new type. Class create/update accept current_type for custom classes only (locked on overrides).

Caveat/tradeoff: the FE connectionRules.js and iOS SLDConnectionRuleService mirror this rule branch-for-branch â€” they must stay in sync. Companion PRs exist in eg-pz-frontend, eg-pz-mobile-iOS, and eg-pz-engineering-ai-pipeline on the same branch name and are not yet merged to dev; they will be ticketed as they land.
