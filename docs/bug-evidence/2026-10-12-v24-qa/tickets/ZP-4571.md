# ZP-4571 — asset-agent 'torque' mode: photos → torque table + amp rating → torque rules (task #68)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, frontend, migration, schema, ui

## Description

### What's the problem

The new Site Data â†’ Torque Rules page needs every torque-eligible asset's torque label read in bulk and staged for review, but the bulk extraction lambda had no mode that reads a torque table (and amp rating) from photos and turns it into torque rules. Separately, a PNG-typed photo could 400 the whole extraction request.

### What's the solution

Adds a \`torque\` mode to the bulk extraction lambda (\_MODES; no ASL change â€” the Map passes items through whole and non-runner modes route to ConfigureAsset). It does a focused vision read of the torque table (plus the amp rating when the asset has none), then a rules step that turns the text into one rule per connection type with conductor sizing (NEC 310.16 / 250.122) computed in code, returning {found, torque_values, rules, amps, amps_read, photo_fp, photo_count}. A read that finds nothing is still a \`done\` result, so the user can accept "none visible".

Skip-unchanged: when photos + read prompt match the photo_fp stamped by the asset's last accepted read, the item is skipped with no model call. torque_rules_core.py is canonical in this repo and vendored to asset-agent-lambda/ and agent-runner/vendored/ (check_vendored.py entry + Dockerfile COPY), with a cross-repo copy in the backend.

Also fixes a bug that affects nameplate mode too: \_b64_image declared the S3 Content-Type for bytes that \_detail() had re-encoded to JPEG, so a PNG-typed photo 400'd the request â€” the type is now sniffed from the bytes. Deploy caveat: deploy this BEFORE the task-#68 backend/frontend surfaces are used â€” an old lambda maps an unknown mode to \`configure\` (the expensive library agent).

Backend arm (be #1426): adds GET /sld/<id>/torque-rules (torque-eligible assets with rules/none_found/pending status, filters, unfiltered stats, ids_only, company gate), a bulk 'torque' mode on /bulk-job (keeps eligible nodes only, skips the voltage graph build; /bulk-job/recent?mode scopes the list and hides page-owned jobs from the asset dialogs), and POST /extraction/torque-agent/apply to accept some/all staged reads in one commit - results read server-side from staged DDB rows, ampere_rating filled only while blank, rules fingerprint stamped so the after-commit hook does not pay twice, emits Ev.TORQUE_RULES_EXTRACTED. New nullable JSONB nodes.torque_extraction stamp via migration tqbulk_a1 (<- swjrnl_a9 <- mrg_tqlock_swjrnl), written by every accepted bulk read and by Extract from Photos. torque_rules_core.py is shared verbatim with the pipeline lambda. Frontend arm (fe #1610): new Site Data -> Data -> Torque Rules page (completion card counting green=has-rules and yellow=read-but-no-values, status/class filters, select-all, rows deep-linking to the asset's Torque Records tab) and TorqueRulesJobDialog (submits mode 'torque', streams staged results, resume a previous run, per-row accept with one Accept selected/all request, shows 'NNNA from label'); services fetchSiteTorqueRules / applyTorqueResults / fetchRecentBulkJobs.
