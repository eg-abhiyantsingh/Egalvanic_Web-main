# ZP-4611 — Task #92: Per-field entity change history (entity_changes) + asset change-history view

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, frontend, migration, schema, ui

## Description

### What's the problem

When an asset's field changed, there was no way to see who changed it, what the old and new values were, or whether the edit came from the web or a queued phone sync. With edits now resolving last-edit-wins per field, one person's overwrite could silently clobber another's value and nobody could trace or untangle it. The asset detail page offered no audit trail at all.

### What's the solution

Backend adds an after_flush listener that records one entity_changes row per changed column across every ORM write path (nodes, edges, issues, tasks, work orders, photos, IR photos, quotes, form / EG-form instances, buildings, floors, rooms, canvas notes), capturing old/new value, user, platform, source (direct / queued / system) and the inbox mutation id in the same transaction as the change. Geometry collapses into a single \_geometry row; \_created / \_deleted markers bookend lifecycle. A new company- and site-scoped GET /entity-history/<node|edge>/<id> returns newest-first history with user names and core attributes expanded per attribute by class definition, with a before cursor for paging.

On the web, the asset detail page gains a three-dot "Change history" item (hidden in the client portal) that opens a dialog rendering one card per save (person, time, web/iOS chip, "Synced from phone" for queued writes), each field shown old -> new, core attributes by name, position/size folded, created/deleted markers, and load-older paging, in English and French. Caveat to carry forward: bulk query.update() and raw SQL writes are NOT captured, and a capture failure is logged but never breaks the save.

### QA Review

* Environment: dev only (not yet in QA).
* On the web asset detail page, edit a node field (label, amps, a core attribute, position) and open the three-dot 'Change history' item; confirm a card for that save shows your name, timestamp, a 'web' chip, and the field's old -> new values.
* Edit a core attribute and confirm it displays by name (e.g. 'KVA Rating 45 kVA -> ...'), not a raw key.
* Make a queued/offline edit from the phone, let it sync, and confirm the resulting card shows a 'Synced from phone' / iOS chip and the queued source.
* Move/resize a node and confirm the position/size change folds into a single geometry entry rather than several rows.
* Confirm creating and deleting an entity produce the \_created / \_deleted markers.
* Confirm load-older paging fetches earlier entries (before cursor) and newest-first ordering holds.
* Confirm the 'Change history' item is hidden in the client portal view.
* Negative: a bulk edit via query.update() / raw SQL is expected NOT to appear in history (documented limitation); confirm a save still succeeds even if history capture errors.
* Add then remove a photo on an asset (incl. a nameplate), open Change history, and confirm Photo added / Photo removed / Photo restored and caption old -> new entries appear, filterable via the Photos field. Dev only.

### Migration - needs review

Migration ehist_a1 (parent mqueue_a1) adds the new entity_changes table. It is purely additive (no column drops or remaps), but confirm it applies cleanly on top of the current head and that the after_flush listener's rows land in the same transaction as the entity change they describe.
