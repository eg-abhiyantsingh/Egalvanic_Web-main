# ZP-4583 — Planned Work v2: unreleased work orders, confirmable schedules, notices, contacts and maintenance calendar

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, backward-compatibility, frontend, migration, schema, ui

## Description

### What's the problem

Maintenance planning lived in a spreadsheet. There were no real work orders behind planned work, no schedule the site and subcontractors could confirm, no contractual notices, and no calendar showing who is booked where. Contacts were typed into free-text fields rather than managed.

### What's the solution

A full planned-work workflow behind the LaunchDarkly flag feature-planned-work-v2.

* Unreleased work orders: ir_sessions.released_at (NULL = planned); POST /ir_session/<id>/release (409 until confirmed). Migration backfills every existing WO as released, so current data is unchanged. Unreleased WOs are hidden on iOS and from schedules, reports, ops counts and v2 lists; the web planned editor keeps them. Planned WOs cannot be closed.
* Schedules + confirmation: session_work_schedules (range, weekdays, shift, exceptions) resolve to work blocks in the site's local time. Lock = Tentative; per-party confirmations move to Partially confirmed / Confirmed; relock creates a revision and clears confirmations. AI can draft and propose dates.
* Notices: generated at create / 6w / 2w / 3d before the first work day (nearest earlier business day, skipping US/CA holidays), with a send log, dedupe and claim-before-send. Jinja email, public token pages to confirm/propose, and an .ics calendar. CLI flask send-schedule-notices; the hourly schedule is created disabled.
* People: crews (in-house Teams and subcontractor crews with mapped contacts and a lead), site/account primary contacts, per-job notice recipients.
* Maintenance calendar: POST /company/<id>/maintenance-calendar returns booked jobs with site-local days and crew lanes; web adds month/week/day, timeline and year-heatmap views with filters.
* Frontend: /planned-work list, planned WO editor, Create/Plan Work Order dialog with schedule+team steps, /maintenance-calendar, Admin Organization (Teams/Subcontractors), Customers/Subcontractors master-detail redesign (View Customer and Accounts pages retired, /accounts/:id redirects to /customers), shared country-driven Add/Edit Site form (timezone now derived from the address), public /schedule-confirmation/:token page.
* Rollout: new backend env vars SCHEDULE_CONFIRM_BASE_URL and SCHEDULE_CALENDAR_BASE_URL per env; enable the hourly notice schedule when ready.

### QA Review

Environment: dev only. Enable LaunchDarkly feature-planned-work-v2 and confirm SCHEDULE_CONFIRM_BASE_URL / SCHEDULE_CALENDAR_BASE_URL are set for dev.

* Create a planned (unreleased) work order; confirm it appears on /planned-work but NOT on iOS, schedules, reports, ops counts or /workorders/v2, and cannot be closed (409).
* Build a schedule, lock it (Tentative), confirm per-party (site + each sub); verify status moves to Partially confirmed then Confirmed; relock and verify it becomes a revision that clears confirmations.
* Release a confirmed WO (POST release); verify it now appears in the normal lists and on iOS; verify release is blocked (409) until confirmed.
* Trigger notices (or run flask send-schedule-notices --dry-run); verify goes-out dates land on the nearest earlier business day, skip US/CA holidays, and dedupe (no double send).
* Open a public /schedule-confirmation/<token> link; confirm and propose different dates; verify the link dies once work starts; download the .ics.
* Check Maintenance Calendar month/week/day, timeline and heatmap views with status/sub/service filters.
* In Admin > Organization manage Teams and Subcontractors (crews, labor-type subsets, contacts with one primary, crew lead); confirm a vendor cannot be given another company's contact.
* Verify migration backfill: existing work orders are all released and behave exactly as before with the flag off.
* Negative: confirm tenant scoping - a user cannot reach another company's vendor, crew, contact or session.
