# ZP-4617 — Task #92: core_attributes_patch - per-attribute node/edge updates (stop cross-client overwrite)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, backward-compatibility, frontend

## Description

### What's the problem

An asset's core_attributes list was replaced wholesale on every save. A client that changed a single attribute still sent its entire list, so its stale copy of every OTHER attribute silently overwrote values another client had just saved. Concrete case: a VCB value set on the web was wiped when Type was changed from the iPad.

### What's the solution

Backend update_node / update_edge now accept a core_attributes_patch containing only the changed attributes, merged by id into the stored list (null / empty clears one); the existing id-normalisation and hidden server-owned-attribute handling then run unchanged. The web editor's changedFields turns a core_attributes change into a patch of only the attributes whose value changed. A full core_attributes list still wins, so older clients behave exactly as before (backward compatible); other entity types keep sending the full list.

### Fixes

* eg-pz-backend #1459 - Task #92: core_attributes_patch - per-attribute updates for nodes and edges
* eg-pz-frontend #1642 - UI Task #92: editor sends changed core attributes as core_attributes_patch

### QA Review

* Environment: dev only (not yet in QA).
* On the web editor set one core attribute (e.g. VCB) on an asset, then from another client/device change a DIFFERENT attribute (e.g. Type) on the same asset; confirm the VCB value survives (is not wiped).
* Clear one attribute (null) via a patch and confirm only that attribute is cleared, the rest intact.
* Confirm an edge core-attribute change behaves the same as a node.
* Backward-compat: a client sending a full core_attributes list still replaces the list wholesale; non-asset/edge entity types still send the full list (unchanged behaviour).
