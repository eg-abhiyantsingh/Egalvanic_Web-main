# ZP-4619 — SLD layout ops skip nodes whose parent is off-canvas (orphan children treated as free nodes)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: frontend, ui

## Description

### What's the problem

On dev, Straighten Downstream and other layout ops silently did nothing for some nodes. A node whose parent had been deleted (e.g. a Relay still pointing at a 'Parent ATS' deleted 2026-02-25) is drawn on the canvas as a free/orphan node, but the editor's buildMaps still mapped it as a child of the missing parent. Layout helpers such as \_straightenFirstDownstream then hit \`if (!parentNode) continue\` and skipped it, so the op found nothing selected (moved.size 0) and nothing moved.

### What's the solution

buildMaps now maps a child only when its parent is actually present on the canvas. An off-canvas (deleted or absent) parent leaves the child as a free node - matching how the canvas already renders it - so layout ops operate on it. Data note: the 2 dangling-parent orphans on the affected dev site had their parent_id cleared; about 38 such orphans exist on dev overall, and the group-delete path that leaves live children behind is called out as a separate follow-up. Pre-existing lint errors at goJSActions.js:180/384 were left untouched.

### Fixes

* eg-pz-frontend #1645 - UI: layout ops treat children of an off-canvas parent as free nodes

### QA Review

* Environment: dev only (cicd/dev).
* On a site with a node whose parent is not on the canvas (an orphan drawn as a free node), select it and run Straighten Downstream / a downstream layout op; confirm the node is now laid out (previously the op did nothing and reported moved.size 0).
* Confirm nodes that DO have a parent on the canvas still lay out as children - no regression to normal parent/child layout.
* Negative: a node with no parent at all still behaves as a free node.
