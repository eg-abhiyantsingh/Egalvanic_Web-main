# ZP-4717 — [Web] Task #135: Normalize and honor a boolean EG form `visible` (backend + renderer)

Status: Ready for QA · Assignee: Eric Ehlert · Labels: api, backend, backward-compatibility, frontend, ui

## Description

### What's the problem

Field teams on P&H Electric hit _"This form has no definition"_ when opening the "Visual & Voltage Inspection" asset form in the mobile app (customer report ZP-4716). Root cause: an EG form definition could store a block's `visible` as a JSON **boolean** (e.g. `"visible": false`) instead of the expected expression **string**. Scripts, MCP and service-spec authoring all wrote raw booleans/numbers. Strict clients (iOS) then failed to decode the whole form; the web renderer had the opposite failure — every call site tested `content.visible` for truthiness, so a boolean `false` read as "no rule" and a block the author meant to keep _always hidden_ was shown instead.

### What's the solution

A two-sided, server-and-client fix so a stray type can neither blank a form nor leak a hidden block:

* **Backend —** `eg_form_builder_service.normalize_v2_visible()` walks the block tree (container children and column children) and rewrites a boolean or number `visible` to `"true"`/`"false"`; strings, absent keys and all other values are left untouched. `coerce_v2_definition` applies it to all three v2 shapes (product create/update routes and the staff update route), and `service_spec_service` applies it before writing service-owned forms — the path P&H's form arrived through.
* **Frontend —** `egFormRendererShared.hasVisibleRule(v)` now treats a rule as present unless the value is `null`, `undefined` or `""`; `evalVisible` / `evalVisibleExpr` return booleans as-is and map numbers by truthiness. Every visibility call site — renderer, builder preview, preview dialog, instance dialog and sessions tab — was moved onto the shared helper.

**Caveat:** this is defensive hardening. A prod scan found **0** forms currently holding a non-string `visible` (the single offending P&H row was corrected by hand); the change stops the type from recurring. Pairs with the client-side tolerant decode in iOS #709 (covered by ZP-4716).

### Fixes

* eg-pz-backend #1495 — Task #135: Store a non-string EG form \`visible\` as an expression string
* eg-pz-frontend #1684 — UI Task #135: Honor a boolean \`visible\` in the EG form renderer

### QA Review

**Environment: dev only** (merged to cicd/dev; not yet in cicd/qa).

* Author/import a V2 EG form whose block carries a boolean visible:false (via a service spec or the product create/update route), save it, and confirm the stored definition now holds the string "false" (not the boolean).
* Open that form on web: the false block stays hidden; a true/absent block stays shown.
* Repeat with visible:true (boolean) and a numeric visible (0 and 1) — 0/false hide, 1/true show.
* Regression: an expression visible (e.g. {{ photos.length > 0 }}) and a plain string "false"/"true" still behave exactly as before; a block with no visible key still renders.
* Negative case: confirm a form that previously showed "This form has no definition" on a strict client now decodes (the P&H Visual & Voltage Inspection definition is the reference fixture).

Originating customer report: ZP-4716 (mobile "form has no definition"). Client companion: iOS #709 (tolerant decode).
