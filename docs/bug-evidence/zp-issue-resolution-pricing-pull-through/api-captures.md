## needs pick — the state exists in code but was not reachable on QA
Added the unresolved SCCR issue (`29ec3afb-…`) to the quote through **Edit Quote → issue picker → Save & Regenerate**. Its line rendered "**no work procedure for this service**" with **no badge and no price** — not "needs pick", and not "awaiting accepted resolution — options: …". The `needs pick` chip needs the server to send `awaiting_resolution` on the coverage entry, which per the ticket only happens for **menu-selection** plan lines; no menu rule exists on QA (corrective services are pruned to one SCCR fix flow and every proposal seen is agent-generated with `implementation_method_id: null`), so the badge could not be produced. The manual resolution's line *does* badge **resolution** ("Thermal Anomaly — BUS5 | Switchboard | QA-DEMO manual fix (delete me) | resolution | —"), so tier-0 attribution also covers manual resolutions.
**Finding — the Add-to-Quote gate does not cover Edit Quote.** The picker let 29 issues (most with no resolution at all) onto the quote in one click; the regenerate produced 29 lines, 28 of them "no work procedure for this service" with no price, while the total stayed $335. So unpriced corrective lines can reach a customer-facing quote through Edit Quote even though **Add to Quote** blocks exactly that. The quote was restored to the single intended issue afterwards (`POST …/generate` with one `issue_ids` entry → coverage 1, `issue_title "SCCR Violation"`, totals $335).
Transient: one `POST …/generate` returned **401** and the immediate retry returned 200 (session refresh mid-call), no data lost.
