## 5 · ZP-3782 — multiselect loses ticked options · STILL OPEN, worse than filed

The ticket says answers are lost. They are — but the end state is worse than "some lost": **the user sees
nothing ticked at all.** Full chain, all of it evidenced today:

1. The field is declared `type: multiselect`, `display: checkbox_list`, with four options
   (Visual Inspection · Insulation Resistance · Contact Resistance · Thermography).
2. The model read **two** and sent them **joined into one string**: `'visual_inspection,thermography'`.
3. The validator compared **that whole string** against the option list and refused it:
   *"`general_info.tests_performed` = 'visual_inspection,thermography' is not one of
   ['contact_resistance','insulation_resistance','thermography','visual_inspection'] (use the option KEY)"*
   — and the warning is emitted **twice**.
4. What persisted is the single string `"visual_inspection"` (`typeof` = string, not an array).
5. **What the inspector sees on screen: 0 of 4 boxes ticked.**

**Root cause, which the ticket does not state:** the validator treats a multiselect as a single-choice
field. It asks `value ∈ options` where it must ask `every(value) ∈ options`. Any multi-value answer can
therefore never validate, whatever the model sends.

**Behaviour has shifted since 9 Sep** — then the key was absent entirely; now one value survives in storage
but none renders. The data loss is unchanged.

Test data: WO `Atest123` https://acme.qa.egalvanic.ai/sessions/465df0c4-39a0-4787-a815-642729c29707 ·
form *Signature Test* · instance `78709624-3686-4bd7-a32f-d7d47ee17250` · asset `BNewasdasd`.

## 6 · ZP-4042 — Maintenance Portal (read-only view, license gating, recorded report history) · NOT READY FOR QA

Jira: **Ready for QA**, Medium, fixVersion Web v2.2, assignee Eric Ehlert. Ticket note: "dev only… not yet
promoted to QA" — tested on QA directly anyway (env field unreliable), and the state is **partial deploy**.

**Finding — the recorded-report-history endpoint 500s deterministically for every role.**
`GET /api/reporting/history?sld_id=…` (per the ticket, "the portal's only query path" for the Reports view)
returns `500 internal_error` with a fresh `trace_id` on every call — with `sld_id`, without it, with a
bogus all-zero id, and with `limit=5` only. Reproduced across **three roles**: CP (Client Portal, customer),
PM (customer), and ADMIN (staff). The sibling `GET /api/reporting/configs` returns **200 JSON** for all three
(positive control), so the reporting blueprint is healthy — only `/reporting/history` faults. An unknown
sibling route returns masked HTML, so `/reporting/history` is a **registered route that always errors**, not
a soft-404.

**Most likely root cause:** the endpoint (code) reached QA but its backing table `report_generations`
(migration `rptgen_a1`) did not — every query hits a missing table → 500.

**Why it is a pre-promotion blocker, not a live outage:** the new customer portal routes
`/maintenance-portal/*` are **not functional on QA** (`/maintenance-portal/reports` → "Access Denied"; no
shipped page calls `/reporting/history`). The live `/maintenance/reports` is the **old report-generation
catalog** (Condition Assessment, EMP Lite, Arc Flash Readiness, Annual Maintenance Report, Asset Service
History, Program Compliance), which calls `/reporting/configs` and works. So no customer hits the 500 today —
but promoting the portal frontend before the migration lands breaks the Reports view on first use.

**Read-only guard (X-EG-Portal negative case) — UNCONFIRMED, not filed.** `node/create` returned identical
`200 received` with and without the header, but node writes are async (200 = queued, not persisted) and the
read-only backend (#1192/#1193) may not be on QA. Inconclusive; needs the guard confirmed present first.

Evidence: `docs/bug-evidence/2026-09-14-zp4042-reporting-history/` — `api-evidence.md` (trace_ids, role
table), `zp4042-portal-reports-access-denied.png` (new portal route not functional),
`zp4042-maintenance-reports-view.png` (old catalog, for contrast).

### 9 · ZP-4038 — Site Overview single-site + Open Issues by Type · SHIPPED, no bug found
`/dashboard` opens on the single picked site (calls `/api/lookup/site-overview/{sld}?company_id=`), no
company-wide “by Site” donut. That endpoint returns `issues_breakdown` (by issue class) + `open_issues_count`.
On site aadcee4c the breakdown sums to **30** classified vs `open_issues_count` **79** — the gap is
**unclassified** open issues (the sampled list carries a `(none)` class), NOT the filed bug. The ZP-4038 bug
would *inflate* the breakdown by counting Resolved/Closed as open; here it is far *smaller*, and mixed-case
statuses (`Open` and `open`) coexist in the data without inflating it → the case-insensitive fix is effective.
Residual: `/api/v2/issues/list` caps at 25 rows (reported total 80) so a full per-class reconcile wasn't possible.
