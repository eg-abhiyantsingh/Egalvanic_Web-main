## 4 · ZP-3783 — option fields ship without their options · STILL OPEN

`GET /api/form-fill/jobs/6293a4f4-.../proposal` → 28 gaps, of which **4 are option-typed**
(radio/select/switch/checkbox). **All 4 carry no `options` key** — only `label, path, section, type, unit`.

The same response's `field_index` **does** carry them for the same field. Example, *Weather Conditions*:
`options: [{clear, Clear}, {rain, Rain}, {overcast, Overcast}]`.

So the data exists in the payload and is simply not attached to the thing the dialog renders. The reviewer
is asked to choose from a list that was never supplied.

## 5 · ZP-3782 — multiselect loses ticked options · STILL OPEN, worse than filed

The ticket says answers are lost. They are — but the end state is worse than "some lost": **the user sees
nothing ticked at all.** Full chain, all of it evidenced today:

1. The field is declared `type: multiselect`, `display: checkbox_list`, with four options
   (Visual Inspection · Insulation Resistance · Contact Resistance · Thermography).
2. The model read **two** and sent them **joined into one string**: `'visual_inspection,thermography'`.
3. The validator compared **that whole string** against the option list and refused it:
   *"`general_info.tests_performed` = 'visual_inspection,thermography' is not one of
   ['contact_resistance','insulation_resistance','thermography','visual_inspection'] (use the option KEY)"*
   — and the warning is emitted **twice**.
4. What persisted is the single string `"visual_inspection"` (`typeof` = string, not an array).
5. **What the inspector sees on screen: 0 of 4 boxes ticked.**

**Root cause, which the ticket does not state:** the validator treats a multiselect as a single-choice
field. It asks `value ∈ options` where it must ask `every(value) ∈ options`. Any multi-value answer can
therefore never validate, whatever the model sends.

**Behaviour has shifted since 9 Sep** — then the key was absent entirely; now one value survives in storage
but none renders. The data loss is unchanged.
