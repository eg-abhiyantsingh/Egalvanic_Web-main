# [Web] Accepting a resolution did not get it onto a quote, minting materials before anyone priced them, with no way to unaccept

**QA verdict — the flow this ticket exists to build works. Accepting a resolution opens the Add to Quote dialog by itself; the dialog offers a new quote or any existing quote on the same site; the Set-prices step collects prices for unpriced parts and writes them onto the quote line and into the materials library; confirming lands you on the quote with the resolution's own labor and materials priced. Acceptance is no longer a one-way door: **Unaccept** returns the resolution to `proposed` and — the negative case that matters — deletes nothing from the library. Minting really has moved off accept: accepting a resolution with an unpriced part left the library untouched at 17 entries; the write happens at quote time. Once quoted the card collapses to **Quoted** with a single **Go to Quote**, and the funnel's Resolution column reads Quoted. Not exercised: appending to an existing quote, the schedule-row work, and the basic-fix regression.**

**Tested:** 2026-09-08 · `acme.qa.egalvanic.ai` build **V1.36**, bundle **`index-CSsDpG3c.js`** · tenant acme · Super Admin seat · live UI clicks with every request captured, materials library counted before and after each acceptance.
**Ticket said "cicd/dev only, not yet promoted to cicd/qa" — wrong:** unaccept, existing-quote targets, the Set-prices step and quote-time minting are all live on QA.

## Findings

### FINDING 1 (Medium) — the schedule-row half of this ticket is inert on QA
`updates_panel_schedule` exists in the method contract and `node_class_has_schedule` correctly identifies Panelboard and Switchboard as schedule-bearing, but not one method on the tenant carries the flag and no corrective service exists to seed it on. The ticket's tradeoff note is the reason this matters: deleting `_execute_swaps` removed the only automatic path that applied a schedule swap, so a schedule change is now recorded **only** when someone completes a `schedule_update` task. With no method flagged, no such task can be minted — so on this tenant the old automatic path is gone and the new manual one cannot fire either. Worth confirming the seeding landed wherever the SCCR fixes actually live.

### FINDING 2 (Low) — no resolution reaches `applied`
Across every issue examined the statuses seen are `proposed`, `accepted` and `superseded`. `applied` is the state the ticket says an accepted resolution moves to when a break/fix form is submitted, and nothing on QA has got there, consistent with no break/fix form being generatable.
