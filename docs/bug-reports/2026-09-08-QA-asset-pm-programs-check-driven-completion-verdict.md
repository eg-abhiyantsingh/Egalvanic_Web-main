# Asset PM maintenance programs, explicit check-off registry, check-driven completion

**QA verdict — five of six web-testable checklist steps PASS on QA and the sixth is PARTIAL. The asset Maintenance tab establishes a program from a Suggested-ranked plan or from directly composed services; per-asset due dates derive from the effective last-serviced (later of customer-stated vs registry) and survive both a line re-tune and a whole-plan replace; the Assets-list bulk configurator applies plans and is gated on a shared asset class, and the legacy PM-designations action is no longer offered from the /assets bulk bar; the work-order wheel is check-driven — a PM Forms service now carries its own ring and one tick moved it live; the de-energized negative gate fires with `skipped_never_shutdown`. One real defect: the BULK dialog gives no pre-apply warning at all — a 4-service plan applied to two never-shutdown assets wrote 1 service each, and the only disclosure was a toast that lasts a few seconds after the fact.**

**Ticket:** [ZP-4019](https://egalvanic.atlassian.net/browse/ZP-4019)
**Artifact:** https://claude.ai/code/artifact/7f56422d-f1ad-45f7-869e-907c058ba8e4

**Ticket said the change was dev-only / not yet promoted.** Wrong for the web half: the Maintenance tab, the plan/custom-program dialog, the bulk configurator, the shutdown gate and the service-named completion rings are all live on QA today.

## Findings

### DEFECT 1 (Medium) — the bulk "Apply PM Plans" dialog gives no pre-apply warning that de-energized lines will be skipped
**Repro:** `/assets` → Bulk Ops → tick **11N-H1-1** and **12N-H1-1** (both Panelboard) → **Shutdown rules** → "Never" → Apply to 2 Assets → with the same two still selected, **Apply PM Plans** → Replace with a PM Plan → "Panelboard (Generic) — Criticality 1" (4 services, 3 of them de-energized) → **Apply to 2 Assets**.
**Actual:** the bulk dialog shows none of the "Won't be set up — can never shut down" labels the single-asset dialog shows — the dialog is one shared component and the /assets call site simply never passes the asset's shutdown restriction to it. The apply returns 200 with `schedules_written: 2`, `skipped_never_shutdown: 6`, `warnings: ["6 de-energized schedule(s) skipped on asset(s) marked as never able to shut down"]`; that warning is pushed as a **toast that lasts a few seconds** (re-verified with the app's own toast element after a first probe with the wrong selector missed it), and nothing durable remains. Both assets end with 1 task (Infrared Thermography) after a 4-service plan was chosen for them.
**Expected:** the bulk dialog flags which lines will be skipped, and for how many of the selected assets, before the user commits — the same disclosure the single-asset dialog gives.
**Why it matters:** the pre-apply labels are what make the gate safe to use, and they are exactly what disappears at the scale where the gate matters most; a transient toast after the write is not a substitute for knowing beforehand. Extrapolated, not observed: on a large mixed selection the skip count scales with the selection and the toast does not.
**Code-observed, not exercised:** the same shared dialog has a third call site on the multi-asset Maintenance Program surface that feeds **one** asset's restriction and history into an apply over many assets — which would give *wrong* disclosure rather than none. Worth a developer's look; it was not driven in this run.

### FINDING 2 (Low) — flipping an asset to "Never shut down" leaves its existing de-energized schedules live
After the bulk Shutdown-rules change to `never`, both assets still held their full 4-line programs with all three de-energized lines still due; the restriction is only consulted when a program is applied. Those schedules disappeared only because the later replace-apply rewrote the program. Nothing flags a now-impossible schedule on an asset that can never be shut down.

### FINDING 3 (Low) — an undated de-energized line keeps its outage-aligned due date after the restriction is relaxed (a persisted wrong date until something re-derives it)
On MAIN-BUS-3836, after `planned_shutdowns_only` aligned the de-energized lines to 1 Mar 2029 and the restriction was set back to "Can shut down anytime", NETA re-derived to its natural 1 Sept 2028 but the undated De-Energized Visual Inspection stayed at the outage-aligned 1 Mar 2029 (it has no anchor to re-derive from). It corrected itself only when a registry date arrived. Not cosmetic: it is a wrong due date that persists until unrelated activity fixes it, and the two lines disagree about which rule they follow.

### FINDING 4 (Low) — two label sets for the same four shutdown values
The asset page says "Can shut down anytime / … — has a bypass / Planned shutdowns only / Can never shut down"; the bulk dialog says "Whenever needed / Whenever needed — has a bypass / Only during planned shutdowns / Never". Same enum (`unrestricted`, `bypass`, `planned_shutdowns_only`, `never`), two vocabularies in one workflow.

### FINDING 5 (Low) — the plan picker shows identical duplicate labels
Searching "Criticality 2" on a Panelboard returns four rows all reading "Panelboard (Generic) — Criticality 2 · Whole class · 4 services": the NFPA 70B global plan plus one copy per tenant standard. Only the group header distinguishes them, and the headers are easy to lose while scrolling a filtered list. The Suggested group has the same shape (three identically named Criticality 1 plans, differing only by the "from <standard>" caption).

### FINDING 6 (Low, API only) — the Locations rail and the header wheel disagree
For the same work order at the same moment, five explicit calls (`mask=arc_flash`, `asset_checks`, `ir_photos`, `checklist`, `com`) returned `arc_flash 2/10`, `asset_checks 5/10`, `ir_photos 0/10`, `checklist 0/0`, `com 0/10`, while `service-completion` returned `arc_flash 5/10`, `asset_checks 4/5`, `ir_photos 1/1`. The mask endpoint's denominators equal the room's asset count and its numerators differ too; **the cause was not isolated at the API level**; the bundle later showed the Locations rail is driven by ONE service's readiness mask (the lowest-priority service wins) while the header wheel sums every service's ring — so the two surfaces are answering different questions by design, and the mismatch is a documentation/UX question rather than a counting bug. The current layout does not print these numbers, so nothing wrong is visible yet.
